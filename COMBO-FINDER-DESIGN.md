# COMBO FINDER - Build Spec

Status: DESIGN SPEC for a brain-chat build. Not yet built. Experimental / educational.
Last updated: 2026-06-22 (brain chat, v4).

## How to use this file
This is a BUILD SPEC, not a run instruction. Building the tool is brain-chat work (the data pipeline, scoring, and gates have to be designed and debugged with Desktop Commander, the way parse_fanduel.py was built). It is NOT a helper run-instruction - there is no tool yet for a helper to execute. Once the tool is built and its rankings pass Damien's eye test, this collapses into a short helper-runnable step.

This tool is experimental and educational. It is NOT a market-edge tool and makes no profit claim. It explores parlay combinations WITHIN a player pool Damien has already chosen (players already on today's board) and attaches data-grounded reasoning. Output is suggestions only; it never places bets and never writes to the live board.

## 0. How to read this spec (REQUIREMENTS vs. METHOD)
This spec separates two things on purpose:
- HARD REQUIREMENTS (Section 4) are non-negotiable. Every one constrains the INTEGRITY OF THE OUTPUT (no meaningless legs, no fabricated or assumed data, no false precision, no leaning on the odds instead of doing the work, no misleading presentation). They are what keep the result from being lazy filler. They do NOT dictate your approach.
- ILLUSTRATIVE / OPEN (Section 5) covers data sources, specific stats, and scoring logic. These are STARTING POINTS, NOT A CEILING. If during the build you find a better source, a stronger driver stat, or a smarter way to score or group, USE IT - you are explicitly encouraged to. The requirements protect the output; they say nothing about your method, and you should improve the method freely. Do not treat the first-guess sources or formulas as the limit of what is allowed.

If a requirement and a better idea ever seem to conflict, the requirement is almost certainly about OUTPUT INTEGRITY (e.g. "do your own analysis before looking at the odds") and the better idea is about METHOD (e.g. "which stat best estimates a steal") - those do not actually conflict. If one genuinely does, surface it to Damien rather than silently dropping the requirement.

## 1. Goal
From the players already on today's board, produce a SMALL, RANKED set of suggested parlays Damien does NOT already hold, each carrying a stated reason rooted in real matchup data AND Claude's own independent probability estimate for each leg.

The primary product is 5-leg combos shaped 2 HR + 2 SB + 1 best-pick (see Section 5, leg count). Suggestions only - no writing to staging.json, no bet placement.

The whole point of the tool is CLAUDE'S OWN MATCHUP READ. Damien can already see the sportsbook odds; he does not need them handed back re-sorted. The tool's value is independent analysis - estimating how likely each leg actually is from real data - and only then comparing that estimate to the market. If the tool ever degrades into "rank by the odds," it has failed its purpose.

## 2. Inputs
- The board (staging.json): the pools - every player with an HR leg, every player with an SB leg, and any other prop legs present - each carried as a (player, prop, game) leg, not a bare name.
- Existing bet signatures: the exact player-sets already held, for exclusion (see R3).
- Per-game matchup context: the external signal that makes a suggestion more than a re-sorted number. This is the fresh-data work and it is the heart of the tool (Section 5).
- Game status per game (start time / live / final): needed for the per-bet-type placement cutoff (R12).
- Odds (OPTIONAL): a saved sportsbook odds file if present on disk, OR the prices already attached to the board's legs. Used LAST and only as a sanity-check on Claude's own estimate, never as a ranking input, after the de-vig handling in R11. If no odds are available the tool runs clean without them. Never the engine. See R10/R11.

## 3. Candidate space (settled with Damien)
Both connection styles are IN - the tool does a MIX OF BOTH (Damien's call):
- Correlated core: legs that share a game and genuinely reinforce each other (knowable before first pitch - see the HR-stack note below).
- Cross-game / variance: independent legs across games, allowed but never described as reinforcing (R7).

Same-game same-player different-prop is also IN (e.g. one player to homer AND steal in one SGP), framed honestly (power and speed rarely co-fire in one game; combined probability stays low even when each leg is fair).

These are the analytical BUILDING BLOCKS, scored separately, then assembled into the 5-leg combos:
1. HR-stack (multiple HR bats, same game)
2. SB-stack (multiple SB threats, same game)
3. Single-player multi-prop (same player, same game, different props)
4. Cross-game / variance (independent legs across games)

IMPORTANT correction on HR-stacks (Damien, 2026-06-22). A same-game HR pair is NOT automatically connected just because the pitcher "might have a bad day." Whether a pitcher is getting hit today is unknowable until the game is underway - which is after this tool runs. The only connection that is knowable beforehand is that BOTH BATTERS profile well against THAT pitcher's style and handedness (e.g. a fly-ball, lefty-vulnerable starter facing two left-handed power bats). The batter side carries the weight, not a presumed pitcher meltdown. Score HR-stacks on what is knowable pre-game: each batter's power profile and platoon edge against this specific pitcher, plus the pitcher's standing HR vulnerability - never on an assumed bad day.

HOW THE BUILDING BLOCKS BECOME THE 5-LEG COMBO (read this so the four buckets do not get treated as four separate output lists). They are the PIECES the combo is assembled from, not four parallel leaderboards:
- HR-stack and SB-stack rankings fill the two HR and two SB slots. Where two of them share a game and the matchup supports a correlated pair, take the pair and flag it correlated; otherwise take the best independent legs.
- Single-player multi-prop is a candidate SOURCE for the 5th best-pick leg (and can also stand alone as a supporting suggestion). It is not its own output list.
- Cross-game / variance is NOT a list of its own - it is the LABEL put on any leg that does not share a game with another leg in the combo (R7). Every leg ends up labeled either correlated (shares a game, reinforcement explained) or independent (cross-game, variance-only).
So the output (Section 6) is the assembled 5-leg combos plus the supporting block rankings underneath - not four separate leaderboards. R6's "rank within each bucket, never a global leaderboard" still governs how the pieces are ranked before assembly.

## 4. HARD REQUIREMENTS (output integrity - non-negotiable)
- R1 - Leg identity. A leg is a (player, prop, game) triple. Never suggest a bare player; a suggestion must always say which prop in which game.
- R2 - Validity gate (runs BEFORE scoring). Reject any candidate that is not: at least 2 distinct (player, prop, game) legs, no duplicate leg, every leg resolvable to a real game today. Same player twice with the SAME prop is rejected; same player with DIFFERENT props is allowed (Section 3).
- R3 - Exclusion of what Damien holds. Exclude only EXACT player-set matches of bets already held. For partial overlaps, ANNOTATE, do not filter ("overlaps your existing bet #xxxx - player Y in both") and let Damien decide.
- R4 - Numeric-citation gate, applied to the INPUTS, not just the output (the anti-laziness gate). Every leg's probability estimate must be built from specific, cited numbers (e.g. a base HR rate, an HR/9, a CS%, an OBP-vs-this-pitcher, a sprint speed) and those numbers must be SHOWN. A rationale with no number ("good hitter in a good spot") is an automatic reject. CRITICAL: replacing the sportsbook's black-box number with Claude's OWN unsupported number is the same laziness in disguise. An estimate is only acceptable if its inputs are cited and visible (base rate, pitcher factor, batter factor, each sourced). Regenerate or drop any leg you cannot support with shown numbers.
- R5 - Insufficient-data path. If the driver data a leg would need is missing, SET IT ASIDE and report it as "insufficient data" - never score or rank it on partial or assumed numbers. Backfilling with assumptions is the laziness in disguise; do not.
- R6 - Ordinal-within-bucket scoring only. Rank candidates WITHIN each bucket. Never produce a single global leaderboard across buckets (they use different drivers and are not comparable), and never present a score as a guaranteed win probability.
- R7 - Correlation honesty. Legs that share a game may be described as reinforcing ONLY where the reinforcement is knowable pre-game (see Section 3 HR-stack correction). Cross-game legs are marked variance-only and it is FORBIDDEN to imply they reinforce each other. Same-game correlation is a DIRECTIONAL adjustment in words, never a fabricated numeric coefficient.
- R8 - Suggestions only. No placing bets, no writing to staging.json or the live board, no calling the add-bet path.
- R9 - Trust rules inherited (same standards as the rest of this project). Verify data with real tool calls; never fabricate a stat or a player; cite the source of a number; say "I do not know" plainly when data is absent. A made-up driver number is worse than no suggestion.
- R10 - ODDS LAST, OPTIONAL, AND SANITY-CHECK ONLY (structural anti-laziness gate). The ranking is ALWAYS Claude's own independent probability estimate - odds are NEVER a ranking input. Do all of your own work first: pull the fresh data, build and SHOW your estimate per leg, and rank the combos before any odds are looked at. Odds are OPTIONAL: if they are available (Damien saved a sportsbook file, OR usable prices are already attached to the legs on the board) they are consulted LAST and only as a final reality-check on your own estimate - a guard that catches you being badly overconfident (you call a guy 35%, the market implies 9%, you are probably the one who is wrong). If no odds are available, the tool runs clean as a pure independent-estimate engine and simply omits the comparison. Never invent odds to fill the gap. Plain version: do the work, rank by your own read, use odds only as a last sanity check if they happen to be there.
- R11 - Odds are not clean probability; de-vig before comparing. A posted price is a probability with the book's margin baked in. Before any odds number is compared to your estimate, de-vig it - convert the odds to implied probability and, where both sides of a market exist, normalize them to sum to 100% so the book's hold is removed. HONEST LIMIT: HR props are usually offered one-sided (just a "to homer" price with no clean opposite to normalize against), so for those the de-vig is APPROXIMATE, not exact - say so rather than implying false precision. STEAM IS OUT OF SCOPE: detecting crowd money requires an opening line and line-movement history, which a single saved snapshot (or the board's current prices) does not contain - so the tool does NOT attempt steam detection. Do not pretend a snapshot reveals line movement. Odds may come from a saved sportsbook file OR from prices already on the board's legs (per-leg only where a leg actually shows its own price; a combined parlay price cannot be split into clean per-leg odds).
- R12 - Per-bet-type placement cutoff (general rule, NOT date-specific). Each bet type has its real placement cutoff and the tool must respect it. A STOLEN-BASE leg cannot be placed once its game has started - exclude SB legs for any game that is live or final. Other bet types may still be placeable after first pitch - keep them unless their own cutoff has passed. Check game status (Section 2) before spending analysis on a leg. This is the general placement rule; do not build any team- or day-specific exception.
- R13 - Shape-fallback honesty (the combo shape can be unfillable). The 2 HR + 2 SB + 1 target is not always achievable - e.g. after R12 removes started-game SB legs, fewer than 2 placeable SB legs may remain, or the board may simply not carry enough of a type. When the eligible pool cannot fill the shape, the tool does NOT force, pad, or fabricate it. It assembles the best valid combo it can from what remains (e.g. 2 HR + 1 SB + 1, or fewer legs), LABELS it as a reduced combo, and states plainly why the full shape could not be built ("only 1 SB leg still placeable - other games started"). A smaller honest combo beats a forced one. If not even a 2-leg valid combo can be formed (R2), say that plainly rather than inventing one.

## 5. ILLUSTRATIVE / OPEN (improve freely - this is NOT a closed list)
Everything here is a STARTING POINT. Treat it as "here is a reasonable first cut" and beat it where you can. Nothing in this section is a restriction. Claude should KNOW to investigate the matchup thoroughly from fresh sources; the named stats below are EXAMPLES of what moves a read, not a checklist that bounds it.

### The engine: your own estimate ranks; odds are an optional reality-check
The core idea (Damien's framing: likeliness of happening vs. the gambling odds). For each leg, estimate its TRUE chance from fresh data, with cited inputs (R4). That estimate is what RANKS the combos - full stop. THEN, only if odds happen to be available, de-vig them (R11), convert to an implied probability, and look at the DIVERGENCE between your estimate and the market - not to re-rank, but as a reality-check on yourself: a large gap (you say 35%, market says 9%) is a flag that you are probably the one who is wrong, so go re-examine your inputs. Present any divergence honestly as "this is where my read differs from the market, and here is why," never as a profit claim. If no odds are available, skip this entirely and rank on your estimate alone. Carry market-efficiency humility throughout: the market is usually right; a divergence is a prompt to re-check your own work, not a guarantee.

### HR-leg drivers (examples, not a checklist)
Opposing starter's home-run vulnerability (HR/9, barrel and hard-hit rate allowed, fly-ball lean) and recent form; the batter's power profile (barrel rate, exit velocity, xSLG - stabilizing metrics, not a 3-game hot streak); SPLITS that move the read - batter vs LHP/RHP, home/away, day/night, recent vs season, and any other split that matters (these are EXAMPLES, not a fixed set of two - investigate whichever splits actually shift this matchup); batter-vs-this-pitcher history (with the honest caveat that career BvP samples are usually tiny and noisy - show the sample size, weight it lightly); lineup slot and expected plate appearances; bullpen exposure. Park factor is a MINOR modifier only - it is a small, well-known effect; note it, do not let it dominate.

### SB-leg drivers (examples, not a checklist) - ON-BASE LEADS
For a steal, the first question is not speed, it is DOES HE GET ON BASE - you cannot steal first. A hit, a walk, or a hit-by-pitch are identical for this purpose: he is on. So the top driver is his on-base likelihood - and the ANCHOR is his STABLE on-base ability (season / recent-season OBP and reach rate over a real sample), because that number is reliable. His reach rate vs THIS pitcher specifically is a useful flavor on top, but treat it with the SAME tiny-sample caution as batter-vs-pitcher HR history (often a handful of career PAs - show the sample, weight it lightly, do not let it override the stable number). Then apply the relevant SPLITS (vs LHP/RHP, home/away, and any split that matters - examples, not a fixed set), which shift the stable rate on a real sample. All of this sits AHEAD of the running-game details, because pop time and pitcher hold are moot if he never reaches. Then the running game: catcher caught-stealing % and pop time; pitcher time-to-plate, how often he is run on, and the success rate allowed; the runner's speed / sprint speed and attempt profile; game state (close-and-late vs blowout). Handedness matters - a left-handed pitcher faces first base and holds runners better, so steal attempts and success against lefties tend to drop (Damien's example - illustrative, the point is Claude should check effects like this on its own).

### Anti-laziness / honesty guardrails (method)
- Build estimates from STABILIZING metrics (barrel rate, exit velo, sprint speed, CS% over real samples), not small-sample or hot-streak noise that overfits.
- Same-game correlation is a directional adjustment in the WORDS of the rationale, never a fabricated numeric coefficient (R7).
- Present every divergence with market-efficiency humility - "where my read differs and why," never an edge or profit claim.
- Show how the inputs combine into the number, with each input sourced (R4) - e.g. start from a base rate and adjust it for the pitcher, the batter, and the matchup. The exact form is open (see the next subsection); what is required is that the path from cited inputs to the final percentage is visible, not a number pulled from nowhere.

### Turning inputs into one number (the crux - method, OPEN)
This is the hard part of the whole tool, and it is deliberately left open - but flagged here so it does not get skipped. The requirements force you to CITE and SHOW the inputs (R4); they do not tell you how to fold HR/9 + barrel rate + park + split into a single "23%". Honest guidance: a base-rate-times-adjustments model is a reasonable start, but naive multiplication of many factors drifts into nonsense (probabilities above 1, or absurdly tiny), so keep the result SANITY-BOUNDED against a sensible base rate - a typical batter's per-game HR chance tops out in the low double digits at most; a steal is gated first by reaching base. Prefer a few strong, stabilizing inputs over many weak ones. Whatever method you choose must be transparent enough that Damien can see why the number landed where it did, and humble enough to come out in a believable range. Improve this freely - just keep it visible and honest.

### De-vig handling (method detail for R11)
De-vig by converting odds to implied probability and, where both sides of a market exist, normalizing them to sum to 100% (removes the book's hold). For one-sided HR props there is no clean opposite to normalize against, so the de-vig is approximate - apply a reasonable hold assumption and label the result approximate rather than implying precision. Source the odds from a saved sportsbook file if present, otherwise from the prices already on the board's legs where a leg shows its own price (a combined parlay price cannot be decomposed into clean per-leg odds). Steam / line-movement is deliberately NOT handled here - it needs line history this tool does not have (see R11).

### Leg count and combo shape (settled with Damien 2026-06-22)
The tool builds 5-LEG combos shaped: at least 2 HR + at least 2 SB + 1 best-pick. The 5TH BEST-PICK LEG defaults to the single remaining leg with Claude's strongest independent read - "strongest" meaning highest estimated probability (the most likely add-on), drawn from any prop on the board including a single-player multi-prop. Because "strongest" can mean different things (most likely vs best value vs biggest longshot), the optimization target for the 5th leg is a RUN-TIME choice; default to most-likely. Damien trims down to a smaller bet himself by removing legs, so the tool assembles the full 5-leg combo WHENEVER THE ELIGIBLE POOL ALLOWS - when it cannot (R13), it builds the best reduced combo it can and says why, rather than forcing the shape. MIX OF BOTH: prefer pairing the 2 HR legs in one game and the 2 SB legs in one game WHERE the matchup genuinely supports a correlated pair (per the HR-stack correction and the SB drivers); otherwise spread across games. Every leg in the output must be LABELED as correlated (shares a game, reinforcement explained) or independent (cross-game, variance-only). A single game rarely offers 2 HR and 2 SB worth taking, so a 5-leg combo typically spans multiple games - label which legs share a game and which do not; never imply a multi-game parlay is one correlated stack. List length N (combos shown) is a run-time input - propose a sane default, do not hard-code.

## 6. Output format
Primary: a ranked list (capped at N) of 5-leg combos, each shaped 2 HR + 2 SB + 1 best-pick. For each combo, show every leg as "player - prop - game" with:
- the leg's independent probability ESTIMATE and the cited numbers behind it (R4);
- the de-vigged market implied probability and the divergence vs your estimate, ONLY when odds are available (a saved file, or the board's own per-leg prices) - omit cleanly when no odds are available, never invent them;
- a correlated-vs-independent label per leg (R7);
- the variance tag on any cross-game grouping;
- the R3 annotation for any partial overlap with a held bet.
Also expose the building-block rankings underneath (best HR bats, best SB threats, and the best-pick / multi-prop candidates that feed the 5th leg) so Damien can see the parts.
Any combo that could not meet the full 2 HR + 2 SB + 1 shape is shown as a labeled REDUCED combo with the reason (R13), not quietly dropped.
Append an "insufficient data - not ranked" list of set-aside legs/candidates with the reason each was set aside (R5), so nothing silently disappears. And list any leg excluded by the R12 cutoff (e.g. SB leg, game already started) so Damien sees why it is gone.

## 7. Build sequencing
- This is a BRAIN-CHAT build, not a helper run - there is no tool yet; the data pipeline, scoring, and gates have to be built and debugged, which is design work.
- NEXT REAL STEP IS A FEASIBILITY PROBE, not more spec text. Before building, a brain chat should actually try to pull each fresh data source for today's slate - probable pitchers, confirmed lineups, OBP / reach rate and key splits, catcher CS% and pop time, pitcher running-game splits, batter Statcast power metrics, and game status - and report what is reachable for free and what is not. Speccing a tool around data that turns out to be unavailable is the main risk; the probe removes it. (Damien's position: there is no good reason the data should be unreachable - the probe is to PROVE that, not to assume it.)
- Then build and PROVE ONE BUCKET first against Damien's eye test (SB-stack or HR-stack is the cleanest start), then widen.
- Once it is built and the rankings pass the eye test, it collapses into a short helper-runnable step ("run the combo finder against today's board, present the combos"), exactly like the parser became the daily run.
- If this becomes code, keep it OUTPUT-ONLY: it must never import or call anything that writes staging.json or touches the live board.
